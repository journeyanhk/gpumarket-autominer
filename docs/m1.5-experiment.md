# M1.5：$15–20 / 48h 纯测量实验

> 目的不是赚钱，是买四个现在拿不到的数：实测 PRL/TH·天、币计量 realizedFactor、spot 真实状态元组、部署成功率。
> 依据：2026-10-26 的实盘竞价价已经贴在盈亏线上（4090 −3%、3090 +5%），"30% 目标"下的出价规则一台都租不到；
> 决策门里「清算价 ≤ 0.8 × 盈亏线」这条今天已判为不成立，不需要再花钱验证。

## 1. 配置（写进 `data/config.json`，或用设置页保存后再改）

| 键 | 值 | 为什么 |
|---|---|---|
| `useSpot` | `true` | 只测竞价；按需价高 30%，测了也没意义 |
| `autoRent` | `false` | 手动下单，避免自动循环一次抢一排 |
| `autoDestroy` | `true` | 部署失败/掉线/被抢要能自己收尾 |
| `targetProfitPct` | `0` | **测量模式**：不要求盈利，只要求"能租到" |
| `stopLossPct` | `-20` | 校验要求 `stopLossPct < targetProfitPct`，目标设 0 时止损必须是负数 |
| `stopLossMinutes` | `60` | 太短会被正常波动打掉，拿不到 24h 数据 |
| `maxInstances` | `2` | 一台 Kryptex、一台 Pearlhash |
| `maxHourlySpend` | `0.3` | 两台 3090 竞价约 $0.22/h |
| `spotBidFactor` | `0.75` | 出价 = 收入 × 0.75，压在上限内 |
| `minBalanceReserve` | `1` | 留一点余额，别让 vast 因余额不足停实例 |

预算：租金约 $11（48h × 2 台 × ~$0.11/h），挖到约 $10–12，**预期净亏 ≤ $5**。

> 出价会精确压在 `min_bid` 上（`Math.max(minBid, want)`），大概率被顶掉——那不是 bug，
> 那正是我们要的状态元组样本。M2 再做出价缓冲（`min_bid × (1+ε)`）。

## 2. 流程

1. 先跑一次体检：`node tools/breakeven.mjs`，确认三路数据都能拿到、价格源有回退。
2. 启动记录器（另开一个窗口，全程不停）：
   ```bash
   node tools/breakeven.mjs --loop 300 --csv data/breakeven.csv
   ```
3. 开控制台（`npm start`），在「市场机会」里手动租两台 3090 竞价机，一台默认 Kryptex、一台 Pearlhash
   （Pearlhash 那台要填 NOCK 地址，否则 NOCK 加成测不出来）。
4. 24h 后把两台的矿池对调（面板上的「切换矿池」），继续跑 24h。
5. 48h 结束：**先销毁全部实例**（`stopped` 仍收磁盘费，这是最容易漏的尾账），再导出
   `data/state.json`、`data/events.log`、`data/breakeven.csv`。

## 3. 判定（交回时看这四样）

| 指标 | 判定 | 数据来源 |
|---|---|---|
| 实测 PRL/TH·天（币计量） | 落在三源哪一侧：Pearlhash / Kryptex / WhatToMine | 矿池到账 ÷ 实际 TH ÷ 小时数 |
| realizedFactor（只算 Kryptex PPS+ 那台） | ≥ 0.92 | 到账 ÷ 理论（成熟窗口 ≥ 24h，币计量） |
| 部署成功率 / 首次出算力时长 | ≥ 2/3 在 20 分钟内 | `deployStats` |
| spot 状态元组 | 收集即可，用来收紧 `preempted` 判定 | `events.log` 里的 `spot 状态变化` |

判定结果决定后续：
- realizedFactor ≥ 0.92 且实测密度不差于中位源 → 进 M2（竞价补位 + 动态出价 + 有效成本）。
- 否则停在 M1，把 `breakeven.mjs --loop` 改成常驻监控；触发条件（任一显卡 `min_bid` ÷ 盈亏线 ≤ 0.8 持续 6h）出现再重启。

## 4. 中止条件

- 单日净亏 > $8（约预算一半）；
- vast API 连续 10 分钟不可用（此时无法退租，只能人工去控制台销毁）；
- 任一台实例 `stopped` 超过 10 分钟仍未销毁（说明监督逻辑没生效，先停下来查）；
- 三路链上数据分歧 > 50% 且持续 1 小时（说明有源坏了，ROI 不可信）。

## 5. 与代码的关系

- 矿工二进制必须过 `miners/manifest.json` 的 sha256（v4 脚本），实验期间不要 `--bump`。
- `tools/breakeven.mjs` 的价格源是 `pearlhash → coingecko(pearl-2) → dexscreener(WPRL/USDT)`；
  三者全挂时它只打印链上数据、不写 CSV，**不会**因为 Cloudflare 质询而退出。
- 已知的口径限制：`accrue()` 只按 GPU 挂牌价记租金，不含存储费、出网带宽、`stopped` 磁盘费，
  所以面板 ROI 一定比真实值**乐观**，判定请以矿池到账为准。

## 6. 实盘发现的 API 漂移（2026-10-26，测得）

跑起来之后核对矿池接口，发现与我们代码里的假设不一致：

| 接口 | 代码假设 | 实际返回（2026-10-26） |
|---|---|---|
| `GET /api/account/{wallet}` | 含 `pending_rewards.total_pending_prl`、`pending_rewards.epochs`、`nock_payout_address` | 只有 `connected_workers`、`estimated_hashrate_15s/60s/5m`、`balance_transactions` |
| `GET /api/nock-balance/{wallet}` | 含 `pending_rewards.total_pending` 与 `epochs` | 只有 `balance`、`balance_transactions` |

影响：

- **NOCK 加成暂时无法从 API 计入**：`nockPerPrl` 没有 epochs 可算、`nockPayoutAddress` 恒为空 →
  `nockBonus = 0`。这是 fail-closed 的方向（ROI 不会被虚高），但意味着 **NOCK 那一条收益轴
  这次测不到**，实验判定只看 PRL。
- 待结算 PRL 也读不到了（只有累计入账 `balance_transactions`）。所以 `realizedFactor` 的分子
  必须用「正数入账累加」这个口径，而不是「余额 + 待结算」。
- 合并挖矿仍然生效：矿工用户名是 `prl1…@nock=<NOCK地址>`（本地已核对拼装正确），
  实际到账要在 Nockchain 侧核对，不能依赖矿池页面。

结论：这次实验把 NOCK 当"额外惊喜"，不作为判定指标；PRL 的 realizedFactor 与实测密度仍然可测。
